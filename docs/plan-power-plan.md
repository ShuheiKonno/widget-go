## 決定事項（2026-10-04、ユーザー確認済み）

- 段階は 3 つ。表記は **「省電力」「バランス」「パフォーマンス」**（性能の低い順）。略称はおまかせ。UI は**スライダー**（当初はボタンだったが、ユーザーの要望で変更）。3 つ目の表記は当初「最適」だったが、ユーザーの要望で「パフォーマンス」に変更した（コード上の識別子 `best` は変えない）。
- **この機能は設定で ON/OFF できる**（2026-10-04、ユーザーの要望。「OFF では元の PC の設定や制御に」）。
  - 設定: `config.json` の `powerModeEnabled`（**既定 OFF**。2026-10-04 に、ユーザーの要望で既定 ON から変更した。OS の電源状態を書き換える機能なので、利用者が設定で ON にしたときだけ働かせる。旧形式の config にキーが無くても OFF。一度でも ON/OFF を操作すると、値が `config.json` に書かれ、以後はその値が使われる）。設定 ⚙ の「電源モードの切替」で切り替える。`/api/setoption?key=powerMode&value=true|false`、`/api/settings` の `powerMode`。
  - **OFF のとき**: 電源モードの読み取りも書き込みも**一切行わない**（`refreshPowerMode` が API を呼ばず `PowerMode` は null）。`/api/powermode` は **403** で拒否する（Win32 を呼ぶ前）。スライダーは隠れる。電源モードは Windows の設定・制御のまま。
  - **見た目は電源モード導入前の仕様に戻す**: クロックのバーはクロックで決まる（ターボ動作中は橙）。トレイの帯も従来どおりクロックの色（通常 `#72b6ff` / ターボ `#ff9f53`）。`PowerMode` が null のとき（OFF、API が使えない環境）に同じ規則を使う。
  - 切替の直後に `kickTray()` を呼び、トレイにも次の周期を待たず反映する。
- **クロックのバーの色は電源モードで決める**（ユーザーの要望。上記の ON のとき）: 省電力 = 緑、バランス = 青（従来の既定色）、パフォーマンス = オレンジ。従来の「ターボ動作中（ベース × 1.02 超）は橙」は廃止する。電源プランがバランス以外・不明な電源モード・取得不可のときは既定の青。**トレイアイコン下端の帯（`tray.go`）も同じ配色にする**（ユーザー確認済み。下記「トレイの帯」）。
- 実体は Windows 11 設定アプリの**電源モード**（overlay）。ラベルはスクリーンショットで確認済み。
- 切替 UI は **CPU 区画の中**に置く。

## 1. 状態モデル

スライダー（overlay）が効くのは、**バランス（またはバランス派生）の電源プランが有効なときだけ**（[Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/customize-power-slider) の「Slider availability」）。T1 でも、バランス以外のプランが有効なとき実効 overlay が `GUID_NULL` になり、バランスと区別できないことを確認した。そのため状態は次の順で決める。

| ① アクティブな電源プラン | ② 実効 overlay | 表示 |
|---|---|---|
| バランス `381b4222-f694-41f0-9685-ff5bb260df2e` | `961cc777-…` | 「省電力」を強調 |
| バランス | `GUID_NULL` | 「バランス」を強調 |
| バランス | `ded574b5-…` | 「パフォーマンス」を強調 |
| バランス | 上記以外（`3af9b8d9-…` など） | どれも強調しない（ツールチップ「不明な電源モード」） |
| **バランス以外**（省電力、高パフォーマンス、OEM 独自など） | — | **スライダーを無効表示**（つまみは隠す）。ツールチップ「電源プランが『バランス』以外のため切り替えできません」 |

- バランス派生の独自プランは v1 では「バランス以外」に含める（GUID が `381b4222` と一致するものだけを対象にする）。
- **電源プランは書き換えない。** 押下で行うのは overlay の設定だけ。ユーザーが選んだ電源プランを黙って変えないための判断で、今回の変更で電源プランの書き込み API（`PowerSetActiveScheme`）は不要になった。
- バッテリー節約機能が有効なときの挙動は T1 の 9 が未検証のため、v1 では特別扱いしない。

### 押下時の処理

1. 現在の電源プランを読む。バランスでなければ何もせず 409 を返す（UI は①で無効にしているが、サーバー側でも拒否する）。
2. `PowerSetActiveOverlayScheme(該当 GUID)` を呼ぶ。失敗したら 500 とエラーコードを返す。
3. UI は応答を待たず、次の 2 秒周期の更新で実際の状態に追従する。失敗時は元の強調へ戻す。

## 2. データソースと API

| 項目 | API | 公式ドキュメント |
|---|---|---|
| 電源プランの取得 | `PowerGetActiveScheme(NULL, &*guid)`（powrprof.dll） | あり（[Learn](https://learn.microsoft.com/en-us/windows/win32/api/powersetting/nf-powersetting-powergetactivescheme)）。返った GUID は `LocalFree` で解放 |
| overlay の取得 | `PowerGetEffectiveOverlayScheme(&guid)` | **なし（非公開）** |
| overlay の設定 | `PowerSetActiveOverlayScheme(&guid)` | **なし（非公開）**。PowerShell Gallery の P/Invoke 例では `int PowerSetActiveOverlayScheme(Guid)` と GUID を値渡し。T1 で **x64 では `&guid`（ポインタ）で動く**ことを確認した |

- **overlay の取得と設定は、公式の裏付けが無い非公開 API。** Learn の電源スライダー文書が裏付けるのは、overlay の GUID と「スライダーはバランス系プランでのみ出る」という点まで。将来の Windows 更新で挙動が変わりうるので、README に書く。
  - 3 つの関数は `proc.Find()` で存在を確認し、1 つでも無ければ **CPU 区画の行ごと非表示**にする。**panic させない**（`docs/plan-gpu-npu.md` の `D3DKMTEnumAdapters3` と同じ扱い）。
- 取得はポーリング（33µs/回）。2 秒周期の収集ループにそのまま乗り、コールバックも登録ハンドルも要らない。
  - 公式の `PowerRegisterForEffectivePowerModeNotifications` も動くが、**電源プランがバランス以外のとき実効モードが更新されない**（T1 の 4）。電源プランを先に見る設計では利点が薄いので採らない。
- 呼び出しは x64 前提（ポインタ渡しの 16 バイト構造体は x64 の呼び出し規約に依存）。リリースは `windows/amd64` のみ（`release.yml`）なので問題ないが、32bit / ARM64 でビルドする場合は再検討が要る点をコードのコメントに残す。
- `powrprof` の `LazyDLL` は `sysinfo/cpufreq.go:18` のものを共有し、**再宣言しない**。CGO は使えない（`release.yml` が `CGO_ENABLED=0`）ので syscall 直叩き。

### AC / DC

overlay は電源接続時とバッテリー駆動時で別々に記憶される。設定アプリにも「電源に接続」「バッテリー駆動」の 2 つのドロップダウンがある（スクリーンショットで確認）。T1 では、AC 接続中の設定でレジストリの `ActiveOverlayAcPowerScheme` **だけ**が、バッテリー駆動中の設定で `ActiveOverlayDcPowerScheme` **だけ**が変わった（§5 の 6）。ウィジェットの 1 行は**今使っている電源側だけ**を表示・操作する。電源を抜き差しすると、表示は 2 秒周期の更新でもう一方の側の値へ切り替わる。

## 3. 表示仕様

CPU 区画のクロックのバー（`.clock-progress`）と CPU モデル名の間に 1 行追加する。

```
💻 CPU                         23%  ▼
[ CPU 使用率バー ]
クロック  3.2 GHz      base 2.4 GHz
[ クロックのバー ]
○──────●──────○                    ← 追加（3 段階のスライダー）
省電力    バランス    パフォーマンス
Intel Core …
```

- **ボタンではなく 3 段階のスライダー**（2026-10-04、ユーザーの要望で変更）。つまみの位置 0 / 1 / 2 が 省電力 / バランス / パフォーマンス に対応し、段階は 3 つ固定（`<input type="range" min="0" max="2" step="1">`）。下のラベルは両端を寄せて中央は中央に置く（つまみの位置と合わせる）。ラベルのクリックでもその段階へ切り替える。
- **ドラッグ中は表示（ラベルの強調）だけ追従し、離したとき（`change`）に 1 回だけ切り替える。** 途中の位置ごとに OS の設定を書き換えない。2 秒周期の更新でつまみが戻らないよう、操作中・切替要求の処理中は描画しない。同じ位置で離したときは何も送らない。
- キー操作（←→）にも対応する（標準のスライダーの挙動）。
- 配色（2026-10-04、ユーザーの要望）: **スライダーも電源モードの色で変える**。省電力 = 緑 `#5bd28e`、バランス = 青 `#72b6ff`、パフォーマンス = 橙 `#ff9f53`（クロックのバーのグラデーションの中間色、トレイの帯と同じ）。つまみ・つまみの位置までの塗り（トラックの左から `0% / 50% / 100%`）・アクティブなラベルの文字に使い、残りのトラックは既存の `--bar-track`。ドラッグ中の途中経過でも色が追従する（離すまで OS には書かない）。ライトテーマではラベルの文字だけ濃い色（`#12905a` / `#2f7fd0` / `#d9650f`）にする。CSS 変数 `--pm-color` / `--pm-text` / `--pm-fill` を `.power-mode.pm-*` で切り替える。電源プランがバランス以外のときはスライダー全体を無効表示にし、**つまみを隠す**（「どの段階とも言えない」ため）。不明な overlay のときも、つまみを隠す。
- 切替失敗時は、押した結果を元の状態へ戻し、トラックを赤くして（4 秒）ツールチップに理由を出す。ダイアログは出さない。
- 幅: 通常表示（230px）では、スライダーの幅 188px にラベルが収まる（T5 で実測済み。「バランス」と「パフォーマンス」の間は 4px と狭い）。ウィンドウを狭めたときは、両端のラベルを省略表示（…）にして中央のラベルと重ならないようにする（200px で「パフォーマンス」が省略される）。高さは約 33px で、ボタン行（約 20px）より少し高い。
- **クロックのバーの色**: `.clock-fill` に `pm-saver`（緑 `#7be0a0 → #3cc47c`）/ `pm-best`（橙 `#ffc46a → #ff7a3c`、従来のターボ色と同じ）を付け外しする。バランスは従来の既定色（青 `#5ad0ff → #8a9cff`）。切替の操作を確定した時点（先に見せる描画を含む）で色が変わり、設定アプリでの変更にも 2 秒周期で追従する。`updateClock` のターボ判定は削除した。
- **トレイの帯**（`tray.go`、「トレイ = CPU 使用率」のとき下端 2px に敷く帯）も同じ配色にする（2026-10-04、ユーザーの要望）。16px では 2 色のグラデーションを表現できないため、バーのグラデーションの中間色を代表色にする: 省電力 `#5bd28e`、バランス `#72b6ff`（従来の通常色と同じ）、パフォーマンス `#ff9f53`（従来のターボ色と同じ）。
  - 判定は `powerModeAccentColor(cachedPower)`（クロックの `clockAccentColor` とターボ判定 `clockTurboRatio` は削除）。電源プランがバランス以外・不明な電源モードのときは青。**電源モードを取得できない環境（`PowerMode` が null）では帯を描かない**（従来の「クロックを取得できない環境では帯なし」と同じ扱い。クロックのバーは常にあるため青）。
  - 切替の直後は `kickTray()` で次の周期を待たずに更新する。設定アプリでの変更は 2 秒周期の更新で追従する。
  - 検証: 代表色が UI のグラデーション両端の中間色であることを単体テストで固定した（`TestPowerAccentIsGradientMidpoint`）。生成したアイコンのピクセルを読み戻し、下端 2 行が期待の色で、その上は背景色であることを確認した（20×20、一時テストで確認後に削除）。実際のトレイ上の見た目の目視は未実施。
- **コンパクト表示（幅 130px）では隠す。** `.compact .clock-row { display:none }`（`ui/index.html:124`）の既存の扱いに合わせる。
- CPU 区画を折りたたむと `.sec-body` ごと隠れる。常時切替したい場合のトレイメニュー追加は将来案（§6）。
- 状態は 2 秒周期で更新するので、設定アプリでの変更にも追従する。

## 4. サーバー層と実装タスク

- `GET /api/powermode?mode=saver|balanced|best`（既存の `/api/topmost?enable=` と同じ GET + `X-Widget-Token`）
  - `mode` は許可リストのみ。それ以外は 400。**クライアントから GUID は受け取らない**（サーバー内の定数へ写像）。
  - 電源プランがバランス以外なら 409。失敗時は 500 とエラーコード。`Config` は変更しない。呼び出しはミューテックスで直列化する。
- 現在値は `SystemData.PowerMode` として `/api/system` に載せる。中身: `planOK`（電源プランがバランスか）、`active`（`saver|balanced|best|other`）。**API が使えない環境や読み取り失敗のときは `null`** で、UI は行ごと隠す（`CPUFreq` が取得不可のとき `null` を返す既存の流儀に合わせ、`supported` フィールドは設けない）。
- 状態コード: 400（mode が許可リスト外）、409（電源プランがバランス以外）、503（API が使えない）、500（設定に失敗。本文に Win32 エラー）、成功は 200 で最新の状態を返す。
- **`config.json` には保存しない。** 電源モードはアプリの設定ではなく OS の状態で、起動時に再適用すると、設定アプリで変えた値を勝手に戻してしまう。`Config` / `HiddenConfig` / `CollapsedConfig` / `defaultOrder` は変更不要。
- **セキュリティ**: 非公開 API で OS の電源状態を書き換える初めての経路になる。`securityMiddleware`（Host 検証 + トークン）の内側に置く現行構成で足りるが、**実装後に `security-reviewer` による確認を必須とする。**

## 5. T1 の結果（2026-10-04 実施）

環境: Windows 11（amd64）、Modern Standby 機（ノート PC）、非昇格。主な検証は**AC 接続中**に行い、**バッテリー駆動中**の検証は電源を抜いた状態で追加実施した（#6）。プローブはスクラッチ領域の使い捨て（`t1probe`）で、**リポジトリには含めていない**。終了時に電源プラン = バランス、overlay = `GUID_NULL` へ復元し、`powercfg /getactivescheme` とレジストリで元どおりであることを確認した。

| # | 結果 | 判定 |
|---|---|---|
| 1 | 「バランス」の overlay は **`GUID_NULL`**。読み取りも書き込みも一貫し、レジストリ（`ActiveOverlayAcPowerScheme`）も `GUID_NULL`。`3af9b8d9` も設定できるが、実効モードは `HighPerformance(3)` になり、設定アプリの「バランス」ではない | 確定 |
| 2 | `PowerSetActiveOverlayScheme` は**非昇格で `rc=0`**。**`&guid`（ポインタ渡し）で動く**。設定後すぐに取得側へ反映 | 通る |
| 3 | 電源プランを省電力 / 高パフォーマンスへ切り替えてバランスに戻すと、overlay は直前の値に復元された | 案 3 では電源プランを書き換えないので影響なし |
| 4 | 電源プランが省電力 / 高パフォーマンスのとき、**実効 overlay は `GUID_NULL` を返す**（保存済みの overlay は変わらない）。実効モード通知は更新されない | §1 の「電源プランを先に見る」の根拠 |
| 5 | 実効モード通知は登録直後と overlay 変更ごとに発火し、値の対応は 0=BatterySaver / 1=BetterBattery / 2=Balanced / 3=HighPerformance / 4=MaxPerformance。設定アプリでの変更で来るかは未検証 | 案 3 では使わない |
| 6 | AC 接続中の操作では `ActiveOverlayAcPowerScheme` **だけ**が変わり、`ActiveOverlayDcPowerScheme` は作られなかった。**バッテリー駆動中（`PowerLineStatus = Offline`）の操作では `ActiveOverlayDcPowerScheme` だけが変わり**、AC 側は `GUID_NULL` のまま。書き込み・読み戻し・各 overlay への切替（省電力 / バランス / 最適）は `rc=0` で、実効 overlay も即座に一致した。**DC 側が未設定のとき、実効 overlay は `961cc777`（最適な電力効率）を返した**（`GUID_NULL` でも `3af9b8d9` でもない）。つまり「未設定の既定値」で表示が食い違う心配はなく、§1 の表をそのまま使える | 確定 |
| 7 | **`PowerSetActiveScheme(究極)` は `rc=50`（`ERROR_NOT_SUPPORTED`）で失敗。** `powercfg /setactive` も「サポートされていない設定への書き込みが試みられました」。省電力と高パフォーマンスは `rc=0` で有効化できた。失敗後の状態は変化なし | **本機では有効化不可 → 究極を外す** |
| 8 | 究極を外したので対象外 | — |
| 9 | 未検証（AC 接続中で、バッテリー節約機能を切り替えていない） | v1 では扱わない |
| 10 | `PowerGetActiveScheme` 47.6µs/回、`PowerGetEffectiveOverlayScheme` 33.0µs/回 | 2 秒周期に乗せて問題なし |

### 未検証として残るもの

- バッテリー節約機能が有効なときの挙動。
- 電源の抜き差しの瞬間の挙動（実装後の手動確認項目。T5）。

検証の副作用: バッテリー側の検証前、`ActiveOverlayDcPowerScheme` はレジストリに値が無かった（実効値は `961cc777`）。復元で「最適な電力効率」を**明示的に設定した**ため、値が `961cc777` として保存された。実効値は変わらない。
- 設定アプリでの変更に追従できること（2 秒周期のポーリングなので、原理的には追従する）。

## 6. 将来案

- 「究極のパフォーマンス」プランの切替。本機では有効化できない。電源プランの複製（`powercfg -duplicatescheme`）で動くかは**未検証**（レジストリへ恒久的に書く操作で、複製元と同じ設定を持つため同じ理由で失敗する可能性が高い）。他の機種で必要になったら、`PowerSetActiveScheme` を使う別機能として再検討する。
- トレイメニューへの追加（`appendUsageMenu` と `ID_TRAY_*` の既存パターン）。ウィンドウ格納中も切替できる。
- 電源プランがバランス以外のときに、スライダー操作でバランスへ戻してから切り替える動作。ユーザーが選んだプランを黙って変える副作用があるため、v1 では採らない。
